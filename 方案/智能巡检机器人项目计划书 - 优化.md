## **云端管理层**

    该层为面向管理人员的服务端，管理人员可轻松使用平台进行相关控制管理相关操作。
    物理链路：Wifi+5G
    视频传输：WebRTC（视频、图片、音频、点云）
    信令控制：MQTT（指令、数据）
    云端框架：K8s + 微服务 + 数字孪生
    远程调试：内网穿透
    编程语言：C#/Go高并发接入（MQTT+WebRTC+K8s）C#复杂业务逻辑（微服务）SQL数据持久化 Js+HTML+CSS前端可视化（交互+WebRTC+数字孪生）
    部署方式：阿里云服务器
    先基于 WebRTC+MQTT 搭建一套最小可行性系统（MVP），跑通“视频回传-远程控制-数据上报”的闭环，后续再逐步叠加数字孪生和AI预测性维护等功能。
### 1. **服务器**

#### 1.1 技术选型（C#/.NET + WebRTC + MQTT）

| 需求              | 推荐技术                                                               |
|:--------------- |:------------------------------------------------------------------ |
| MQTT Broker（本地） | EMQX（或 Mosquitto），但 .NET 可用 `MQTTnet` 实现轻量级 Broker（可选）             |
| MQTT 客户端（后端）    | `MQTTnet`（连接 Broker，订阅/发布消息）                                       |
| WebRTC 信令服务器    | [ASP.NET](https://asp.net/) Core + WebSocket（或用 SignalR 作为信令通道）    |
| WebRTC 媒体服务器    | **Janus** 或 **SRS**（支持 WebRTC），.NET 通过 HTTP API 控制房间/推流            |
| 实时视频流处理         | 前端（浏览器/App）使用 WebRTC 直接推流/拉流，.NET 不直接处理媒体流                         |
| 后端框架            | [ASP.NET](https://asp.net/) Core 8.0（WebAPI + SignalR + WebSocket） |
| 数据存储            | PostgreSQL + EF Core（关系数据） + InfluxDB（时序数据） + MinIO（视频截图）          |
| 设备/用户认证         | JWT + [ASP.NET](https://asp.net/) Core Identity                    |
| 容器化部署           | Docker + Docker Compose（包含 EMQX、Janus、数据库、.NET 服务）                 |

**为什么需要媒体服务器（SFU）？**  
矿山环境下网络复杂，P2P 可能穿透失败，使用 SFU（如 Janus）可保证所有客户端都能稳定接收视频流，且 .NET 后端只需控制房间和流权限。

#### 1.2 整体架构调整（融入 WebRTC 与 MQTT）

```plain
[机器人端]                      [系统层 - 本地服务器]                  [前端]
   │                                    │                              │
   │── MQTT (传感器数据/状态) ──────────►│ MQTT Broker ◄─────────────── │
   │                                    │ (EMQX)                        │
   │◄── MQTT (控制指令) ────────────────│                               │
   │                                    │                               │
   │── WebRTC (视频流) ────────────────►│ WebRTC SFU (Janus) ◄───────── │
   │                                    │ (转发视频流)                   │
   │                                    │                               │
   │                                    │ .NET 后端服务                 │
   │                                    │ - 信令服务器 (WebSocket)       │
   │                                    │ - MQTT 数据接入/处理           │
   │                                    │ - 设备管理/认证/存储           │
   │                                    │ - 本地-云端同步                │
```



+ **机器人端**：需要集成 WebRTC 推流库（如 GStreamer + libwebrtc）或使用现成方案（如树莓派 + pion/webrtc）。
+ **系统层（.NET）**：重点实现 MQTT 数据处理、信令交换、控制 Janus 创建/销毁房间。
+ **前端**：浏览器（电脑网页端）或手机 App（手持终端）通过 WebRTC 拉流，通过 MQTT over WebSocket 接收实时数据。

### 3.决策系统

        以ROS2机器人操作系统作为框架，各个模块以Node为单位，通信中间件统一采用DDS数据分发服务，通信方式为话题Topic、服务Service、动作Action，载体为消息Message，模块拥有方法Method(写)、数据Data(读)两种接口，各个模块为异步通信即各个进程。以C++为主、Python为辅。

#### 3.1公共层

        该层作为贯穿所有层的隐形支柱，不参与ros2节点化，负责安全、诊断、日志、配置、全局时间同步等公共功能。

#### 3.2驱动层

        该层将物理设备接口Node化，将Method与Data以Message封装并提供全局DDS通信方式。如将Camera Node化，
    提供/camera/color/camera_info、/camera/color/image_raw、/camera/depth/camera_info、/camera/depth/image_raw通信方式，消息格式自定义。
    步骤：物理接口->驱动代码->将Method与Data封装为Message->提供通信方式->Node化
    举例：USB3.0->相机驱动->将配置方法与图像数据封装为消息->通信方式为话题->节点化
    使用：Luanch文件启动各个Node并启动mian接口->Node之间使用各自约定的通信方式通信->消息载体传输->收到消息->各个处理

#### 3.3算法层

       使用驱动层Node的基础数据构建算法模块Node，如以/lidar/points_raw为数据源，加载SLAM库，处理完成后发布为/slam/map/now。
    如使用/camera/depth/image_raw和/camera/depth/image_raw为数据源，加载OpenCV与YOLO库，处理完发布/yolo/obj/center_point、 /opencv/obj/center_distance。

#### 3.4应用层

        使用算法层和驱动层以及应用层Node构建应用，如使用/slam/map/now为数据源、/chassis/control/method为方法源加载PNC库，处理完后订            阅/pnc/map/obj_point。实现当前位置到目标航点的的应用。
    	如使用/pnc/map/obj_point、/yolo/obj/center_point、/opencv/obj/center_distance、/getway/comms/to_cloud实现导航并途中检测目标，然后记录数 据上传到云端。

#### 3.5二开层

    	该层将功能节点封装为RPC接口，即使用http作为通信方式用于二次开发，屏蔽了开发语言的差异性，任何支持http的语言都可以进行二次开发。

#### 3.6任务层

    	该层以任务为单位，无论是应用层任务还是二开层任务，都需要放入该层注册，由系统状态机、行为树进行任务编排调度，是全局大脑。
    	同时可接入大模型（二次开发者）作为拟人角色使用RPC接口发布任务参与编排。
    	如注册了电量低返航充电任务、巡航任务、检测任务，该层会执行巡航、中途调用检测、电量低时触发返航充电。它不再关注底层的“怎么动”（那是应用层的事），而是关	注“做什么”和“按什么顺序做”。
    	该层由任务注册模块、任务编排模块（行为树BehaviorTree.CPP、py_trees）、调度仲裁模块构成。

## **实时运控层**

        该层作为整机小脑部分，负责机体的实时运控与扩展系统，该部分使用EtherCAT工业以太网与下层通信保证微秒级别的实时性，与电机和扩展MCU模块通信，软件上使用预设动作+实时姿态解算保证复杂地形的平衡和活动，小脑作为整机的命脉决策部分，应从简设计。

### 1. **主控系统**

        采用RK3588作为主控器，成熟的工业开发方案，拥有4大核+4小核的CPU、同时支持6Tops的AI算力，作为工业开发板还具有成熟的IgH EtherCAT软主站官方支持。完美支持EtherCAT+Ethernet通信、以及运控解算任务。

#### 1.1硬件

                     主控：野火RK3588(4+32GB)(有EtherCAT教程，最终效果抖动仅4.8us) or  购买核心板+自设计散热+双网口+电源+调试UART底板

#### 1.2软件

                     软件：Ubuntu22.04 Server无桌面版+ ROS2 Humble + PREEMPT-RT + IgH EtherCAT

#### 1.3接口分配

                    网口1：用于EtherCAT主站通信
                    网口2：用于与大脑通信
                    UART：用于调试使用



### 2.决策系统

            ROS2框架。

#### 2.1公共层

                    该层作为贯穿所有层的隐形支柱，不参与ros2节点化，负责安全、诊断、日志、配置、全局时间同步等公共功能。

#### 2.2接口层

##### 实时接口：

                    EtherCAT 通信部分，1KHz更新从站数据（RTK、IMU、编码器），封装数据与控制指令为C++类，不参与ros2节点化。
                    EtherCAT 算法部分：如PID控制、传感器融合算法封装为C++类，不参与ros2节点化

##### 非实时接口：

                    Ethernet 收发，解析封装数据与控制指令为DDS通信接口，封装为节点，方便与大脑通信。

#### 2.3算法层

                    使用接口层数据完成通信模块、tf2、nav2等功能并封装为节点，提供DDS通信方式和消息。
                    如ros2 nav2 输出速度->实时接口直接控制电机

#### 2.4应用层

                    将算法层各个部分联系起来。

##### 公共层

            1.func_config.h 全局功能配置

            3.memory_overrides.c全局内存重载管理

##### 主要功能框架 统一板子句柄管理 Board* GetInstanc()：

            1.virtual registerDevice = 0; 注册挂载设备
            2.virtual getBoardInfo = 0 板子信息描述
            3.virtual resetSystem = 0; 系统复位
            5.virtual void wdgFeed() = 0; 喂狗
            6.InputDeviceManager inputDeviceManager 输入设备管理器
                6.1 设备类型：PeriodicRefresher周期刷新器、SynchronousAcquirer同步获取器、EventDriver事件驱动器
                6.2 外部接口：addInputDevice 注册输入设备、getInputDevice 获取输入设备、registerCallback 注册后台回调任务
                6.3 后台任务：后台任务根据时钟周期和设备类型自动调度更新数据
                6.4 信用机制：当设备更新耗时未在1个周期内完成，加入失信列表，优先级降低，正常后恢复。
            7.IOStreamDeviceManager 输入输出流设备管理器
                7.1外部接口：addIOStreamDevice 增加流设备、getIOStreamDevice 获取流设备
                7.2设备功能：output 输出数据、stringOutput 字符串输出数据、cFormatOutput C格式化输出数据、input 输入数据
            8.MotorManager 电机设备管理器
                暂不使用，这里的电机抽象交给输入输出流设备管理器完成。
